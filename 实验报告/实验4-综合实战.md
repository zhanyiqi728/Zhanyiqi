## 四、实验内容

在实验三（二）基础上，通过面向接口编程与任务编排进一步重构，并新增掉头指令 `TR` 及不同车辆类型支持（对应需求文档《需求4-支持掉头功能》与课后综合作业《支持不同的车辆类型》）：

- 基础指令：`M` 前进、`L` 左转、`R` 右转。
- 加速指令 `F`、倒车指令 `B`：切换对应状态，语义与实验三一致。
- 掉头指令 `TR`：正常时左转 90 → 前进 1 → 左转 90；加速时前进 1 → 左转 90 → 前进 1 → 左转 90；倒车状态忽略。
- 支持车辆类型：`Normal` 普通车、`Bus` 大巴、`SportsCar` 跑车，`M/L/R` 语义随类型变化（详见下表）。

**三种车辆类型的指令语义**：

| 车辆类型 | `M`（正常/加速） | `L`/`R` 语义 |
| --- | --- | --- |
| Normal 普通车 | 前进 1 格 / 2 格 | 仅转向（加速时先移动 1 格再转向） |
| Bus 大巴 | 前进 1 格 / 2 格 | 先移动 1 格（加速 2 格）再转向 |
| SportsCar 跑车 | 前进 2 格 / 4 格 | 先转向再移动 1 格（加速时前后各移动 1 格） |

倒车状态下：`M` 后退、`L/R` 反向转向，与各类型正常语义对应。

## 六、实验步骤及操作

**1. 面向接口编程：单例与指令工厂**

`Singleton<T>` 用 C++11 起函数内静态局部变量的线程安全初始化实现单例；`CmderFactory` 持有指令表并只构建一次，`Cmder = std::function<ActionGroup(PoseHandler&)>` 用别名简化签名：

```cpp
template <typename T> class Singleton final {
public:
    static T& Instance() noexcept { static T instance; return instance; }
};

class CmderFactory final {
    const std::unordered_map<char, Cmder> cmderMap {
        {'M', MoveCommand()}, {'L', TurnLeftCommand()}, {'R', TurnRightCommand()},
        {'Z', TurnRoundCommand()}, {'B', ReverseCommand()}, {'F', FastCommand()},
    };
public:
    CmderList GetCmders(const std::string& commands) const noexcept;
};
```

**2. 任务编排：原子动作与动作组**

`ActionType` 枚举定义 8 种原子动作，`ActionGroup` 负责收集与执行；指令不再直接操作状态，而是返回编排好的动作组：

```cpp
enum class ActionType : uint16_t {
    FORWARD_1_STEP_ACTION, BACKWARD_1_STEP_ACTION,
    TURNLEFT_ACTION, REVERSE_TURNLEFT_ACTION,
    TURNRIGHT_ACTION, REVERSE_TURNRIGHT_ACTION,
    BE_FAST_ACTION, BE_REVERSE_ACTION,
};
```

`ActionGroup::DoOperate` 通过动作表（`std::vector<std::function<...>>`）把 `ActionType` 映射为具体操作并顺序执行。

**3. 掉头指令解析**

`CmderFactory` 先把 `TR` 替换为占位符 `Z`，再把 `Z` 映射到 `TurnRoundCommand`，避免与 `R`（右转）冲突：

```cpp
std::string ParseCommandString(std::string_view commands) const noexcept {
    std::string result(commands);
    ReplaceAll(result, "TR", "Z");
    return result;
}
```

`TurnRoundCommand` 按状态返回不同动作组：正常 `{TURNLEFT, FORWARD, TURNLEFT}`，加速 `{FORWARD, TURNLEFT, FORWARD, TURNLEFT}`，倒车返回空组（忽略）。

**4. 多车辆类型（作业）**

`Executor::NewExecutor(pose, type)` 通过 `VehicleType` 选择车辆类型；`PoseHandler` 保存类型，指令函数对象据此编排动作组。以 `TurnLeftCommand` 为例：

```cpp
ActionGroup operator()(PoseHandler& h) const noexcept {
    const auto step = h.IsReverse() ? BACKWARD_1_STEP_ACTION : FORWARD_1_STEP_ACTION;
    const auto turn = h.IsReverse() ? REVERSE_TURNLEFT_ACTION : TURNLEFT_ACTION;
    switch (h.GetVehicleType()) {
        case VehicleType::Bus:        // 先移动（加速 2 格）再转向
        case VehicleType::SportsCar:  // 先转向再移动（加速前后各 1 格）
        case VehicleType::Normal:     // 仅转向（加速先移动 1 格）
    }
}
```

## 十、总结及心得体会

1. 任务编排把"指令解析"与"动作执行"解耦：指令负责产出动作组，`ActionGroup` 统一执行，逻辑清晰、易于扩展复杂指令（如 `TR`）。
2. 面向接口编程让 `ExecutorImpl` 只依赖 `CmderFactory` 接口，通过单例复用指令表，避免了重复构建的开销。
3. 用占位符替换解析 `TR` 是一个实用技巧，解决了多字符指令与单字符指令的解析冲突。
4. 支持多车辆类型时，将类型信息保存在 `PoseHandler` 中、由指令函数对象据此编排动作组，是"策略随上下文变化"的典型做法，代码可读性与可维护性良好。

## 十一、对本实验过程及方法、手段的改进建议

1. 车辆类型与指令语义的映射目前分散在各指令函数对象的 `switch` 中，可考虑进一步抽象为"车辆行为策略"对象，集中管理。
2. 掉头指令采用字符串替换 `TR`→`Z`，若未来出现更多多字符指令，可引入更通用的指令解析器（如扫描器/状态机）。
3. 测试用例较多且手工维护，可引入参数化测试或数据驱动测试框架，减少重复代码、提升用例可维护性。
